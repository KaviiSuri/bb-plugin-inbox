# The fork of bb's thread-list

This plugin is a fork of bb's built-in sidebar thread list,
[`get-bb/bb` `plugins/thread-list`](https://github.com/get-bb/bb/tree/55135d1e5045d6c5d3c24f5a4d5556ed3e11cb00/plugins/thread-list)
(MIT, see `LICENSE.upstream`). Upstream files sit at the repository root at
the same relative paths they have under `plugins/thread-list/`.

## Pin

`upstream.json` records the upstream commit the fork tracks:

- commit `55135d1e5045d6c5d3c24f5a4d5556ed3e11cb00` (2026-11-07, "Open the
  sidebar update card in a drawer on touch and match the footer icons (#7237)")
- `@get-bb/plugin-sdk` `0.6.133`, the SDK version at that commit and npm
  `latest` when forked. bb 0.49.0 ships SDK 0.6.132; `plugins/thread-list`
  is byte-identical between bb's `desktop-v0.49.0` tag and the pin, so the
  fork uses no API newer than the host has. `bb plugin build` prints a pin
  mismatch note on bb 0.49.0; it's harmless (same SDK major).

The first commit on the fork branch, "Import upstream plugins/thread-list at
get-bb/bb 55135d1e verbatim", is the pristine upstream copy. Every change
after it falls into one of the four kinds below.

## What differs from upstream

### 1. Generated by `scripts/fork-upstream.mjs vendor`

These are rewritten from upstream on every `vendor` run. Don't edit them by
hand; change the script's `FORK_MANIFEST` / `FORK_TSCONFIG_INCLUDE` instead.

- `components/ui/**`, `hooks/**`, `lib/**`: bb component registry items
  (`packages/plugin-registry/r/*.json` at the pin) for every `@/` import,
  plus their registry dependencies. Upstream maps `@/` onto bb's
  `packages/shared-ui/src`; these are the same sources as published by the
  registry. Selection and writing are upstream's own
  `scripts/lib/plugin-fork.mjs` (`registryAliasImports`,
  `registryItemsForImports`), the code its "Plugin Fork Check" CI runs.
- `package.json`: upstream's, passed through `forkPluginPackageJson`
  (drops `@bb/shared-ui`, `@bb/plugin-build` and the `prepare:bundled` script,
  pins `@get-bb/plugin-sdk`, adds the registry items' packages), then
  `FORK_MANIFEST`: `name` `bb-plugin-inbox`, `description`, `bb.name`
  `Inbox`, `bb.description`, and a `build` script.
- `tsconfig.json`: upstream's, passed through `forkPluginTsconfig`
  (`paths` → `{"@/*": ["./*"]}`), plus `fork.test.ts` in `include`.

### 2. Renames so the fork runs beside the built-in list

The package name sets the plugin id (`inbox`), so the CLI (`bb inbox`), the
KV namespace, the realtime channel and the localStorage mirror
(`bb.inbox.preferences.v1`) all move with it. The literal ids upstream
hard-codes:

| File | Upstream | Fork |
|---|---|---|
| `app.tsx:36-39` | slot `id: "thread-list"`, `title: "Thread list"`, its description | `id: "inbox"`, `title: "Inbox"`, a description naming the Inbox tab |
| `app/rows/ThreadRow.tsx:290` | `"thread-list/customizeRowActions"` | `"inbox/customizeRowActions"` |
| `shared/preferences.ts:42` | legacy `move: "thread-list/move"` | `move: "inbox/move"` |
| `shared/preferences.ts:184` | `thread-list/move` in the `rowActions` description | `inbox/move` |
| `skills/thread-list/SKILL.md` | path, `name: thread-list`, `bb thread-list prefs`, `thread-list/move`, title and opening line | moved to `skills/inbox/SKILL.md`; `name: inbox`, `bb inbox prefs`, `inbox/move`, and says it's the fork |

Test expectations that name those ids, updated to the new ids and otherwise
unchanged:

| File | Upstream | Fork |
|---|---|---|
| `app.test.tsx:373` | `expect(registration.id).toBe("thread-list")` | `.toBe("inbox")` |
| `server.test.ts:159` | `["thread-list/move", "push-notifications/level"]` | `["inbox/move", …]` |
| `server.test.ts:192` | `"thread-list/move"` | `"inbox/move"` |

Left alone on purpose: tests that pass `"thread-list"` as an arbitrary plugin
id to the harness (`server.test.ts:6`, `app.test.tsx:374`,
`app/preferences/preferences-sync.test.ts`), tests that mock host actions

`app/list/ThreadRowActionsCustomize.test.tsx`), the vitest project name, DOM
test ids (`sidebar-thread-list-*`), and `PLUGIN_OVERVIEW.md`. None of these
collide at runtime.

### 3. Fork-owned files (no upstream counterpart)

`upstream.json`, `scripts/fork-upstream.mjs`, `fork.test.ts` (runs
`experimental_scanPublicSdkOnly`, checks every `@/` import resolves inside
the package, and fails if the plugin id is `thread-list` or any runtime source
hard-codes a `thread-list` / `thread-list/<key>` literal, so an upstream merge
that brings one back goes red), `components.json` (shadcn registry pinned to the same commit,
for `npx shadcn add @bb/<item>`), `.gitignore`, `package-lock.json`,
`LICENSE.upstream`, and the repository's own docs (`README.md`, `AGENTS.md`,
`CONTEXT.md`, `docs/`).

### 4. Changes to upstream code

Inbox code lives in `app/inbox/`, `server/verification/`,
`shared/inbox-preferences.ts` and `shared/inbox-verification.ts`, and touches
upstream files only at the seams the spec names (root component, preference
definitions, server). Each such change:

| File | Change | Why |
|---|---|---|
| `app.tsx` | `ThreadList` renders `InboxTabs` (from `app/inbox/InboxTabs.tsx`) inside the same providers, passing upstream's list as its Threads tab; `useSidebarThreadReveal()` and `<ProjectList>` move into a small `ThreadsTab` component in the same file | The Threads \| Inbox switch (#11). The reveal hook runs only while the Threads tab is mounted, so revealing the active thread is skipped while the Inbox shows |
| `shared/preferences.ts` | imports `inboxPreferenceDefinitions` from `./inbox-preferences.js` and spreads it at the end of `preferenceDefinitions` | The Inbox's synced preferences (`activeTab`, #11) share upstream's KV, realtime channel, localStorage mirror and `bb inbox prefs` CLI |
| `skills/inbox/SKILL.md` | lists `activeTab` among the keys and says what it does | Documents the new preference |
| `server.ts` | imports `registerVerification` from `./server/verification/index.js` and calls it at the top of the factory | Verifications and Laters: their storage, keyed reads and mutations (#12) |
| `app.test.tsx:215` | the "renders pinned, custom sections…" test checks only the preference RPC calls (`method.includes("Preference")`), not every RPC call | The Inbox tab's count reads Verifications, Laters and evidence even while the Threads tab shows |

Not a file change, but worth knowing on a merge: `app/inbox/InboxTabs.tsx`
offsets upstream's sticky headers below the tab bar with an unlayered
`<style>` that overrides the host's `--bb-sidebar-sticky-label-top`,
`--bb-sidebar-sticky-project-top` and the stack's `::before` `top`. If an
upstream or bb release renames those custom properties, the Threads tab's
sticky headers slide under the tab bar; update the CSS there.

## Decided: left as upstream

Both decided by the user on PR #16 (2026-11-09), to keep upstream merges
mechanical:

- **Tap targets.** Upstream's Threads list sizes some controls under 40px on
  a coarse pointer (group header buttons 32–36px, collapse chevrons 20–24px,
  nested child rows 36px), the same as bb's built-in list. The Threads tab
  keeps upstream's sizes; only the Inbox tab must meet 40px.
- **Duplicate "Move to section".** Both plugins register it (`thread-list/move`
  and `inbox/move`), and thread action menus are additive, so with both
  enabled and organized chronologically the menu shows it twice. Accepted: it
  goes away once the built-in list is disabled.

## Merging upstream later

```sh
node scripts/fork-upstream.mjs merge <upstream-commit>   # e.g. a bb release tag's sha
npm install --legacy-peer-deps
npm run typecheck && npm test && bb plugin build .
```

`merge` makes a sparse clone of get-bb/bb (or uses `--bb <checkout>`), then
for every file under `plugins/thread-list/` that changed between the pin and
`<commit>` runs `git merge-file <fork file> <upstream at pin> <upstream at
commit>`, honouring the path renames above. Files upstream deleted are
removed when the fork hadn't changed them. It then moves the pin in
`upstream.json` and runs `vendor` against the new commit, so the registry
items, `package.json` and `tsconfig.json` follow upstream. Conflicts are
listed and the command exits 1; resolve the conflict markers, update the
tables above if a rename moved, and commit.

`node scripts/fork-upstream.mjs vendor` on its own regenerates the generated
files at the current pin; a clean `git status` afterwards means they're in
sync. `vendor` never deletes a vendored file; when an upgrade stops needing a
registry item, remove its files by hand (`fork.test.ts` still passes either
way).
